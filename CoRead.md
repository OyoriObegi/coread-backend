The first task for the Antigravity agent is building the stateless conversion service inside the `coread-converter` directory. The agent must create a `main.py` file using FastAPI and PyMuPDF (`fitz`), alongside `ebooklib` and `BeautifulSoup4` for EPUB parsing. The service requires a `GET /health` endpoint that returns a 200 status code so the CoRead Android client can wake the Render container from cold starts before sending large files. The primary endpoint must be `POST /convert`, which accepts a multipart file upload, a `groupId` string, and a `bookId` string. When a file arrives, the script saves it to a temporary directory and checks the file extension. For PDFs, PyMuPDF iterates through every page to inspect text blocks. If the first five pages contain zero extractable characters, the endpoint immediately returns a 422 status error stating that scanned image PDFs are unsupported. Otherwise, the script extracts the table of contents using `doc.get_toc()`. If the table of contents is empty, the script calculates the median font size across the document and flags any text line exceeding that median by twenty percent as a chapter heading. It then merges lines into contiguous paragraphs, strips repeating header and footer page numbers, and counts the words in each paragraph using whitespace splitting. The output is a flat JSON object containing the book metadata, a list of chapter markers linked to starting paragraph indices, and an array of paragraph objects where each object holds a sequential `index` integer, a `text` string, and a `wordCount` integer. Using the `firebase-admin` SDK initialized via environment variables, the Python script uploads this gzip-compressed JSON file directly to Firebase Cloud Storage at `groups/{groupId}/books/{bookId}.json` and returns the download URL and total paragraph count to the client. The agent must generate a `Dockerfile` and a `requirements.txt` file, verify the endpoint locally using `pytest`, and provide a walkthrough artifact for deploying the `coread-converter` repository to Render.

The second task is configuring the Firebase backend and security rules for CoRead. The agent must generate a `firestore.rules` file and a `storage.rules` file that enforce strict group-level isolation. Every document in the `groups/{groupId}` collection must contain a `memberIds` array of Firebase Authentication UIDs and an `invitedEmails` array. The security rules must verify that `request.auth.uid in resource.data.memberIds` for all read and write operations, while allowing a newly authenticated user whose email matches an entry in `invitedEmails` to append their UID to `memberIds`. Inside each group document, the schema must track `activeBookId`, `currentDayNumber`, `startParagraphIndex`, `endParagraphIndex`, `dailyTargetType` (set to chapters, words, or custom), `dailyTargetValue`, `streakCount`, `lastStreakEvalDate`, `pauseTokensRemaining` (initialized to 3 per month), and `pauseRequestedBy`. Each group document will have three subcollections: `members` for tracking individual reading positions and last-active timestamps, `commentaries` for storing daily reflections and peer critiques, and `messages` for the general group chat.

The third task is building the local data layer in the `coread-android` project under the `com.coread.app.data` package using Room and Preferences DataStore. Because downloading a book JSON from Firebase Storage on every app launch wastes bandwidth, the agent must build a `CoReadDatabase` in Room with three entities: `BookParagraphEntity`, `ChapterMarkerEntity`, and `ReadingSessionLogEntity`. When a group starts a book, the app first pings the Render `GET /health` endpoint during upload, and once converted, downloads the compressed JSON file once. The app streams the JSON through `kotlinx.serialization.json` without loading the entire file into memory at once, and inserts the paragraphs into Room in a single database transaction. The `ReadingSessionLogEntity` table records every reading session with `startTime`, `endTime`, `paragraphsRead`, and `averageWpm` so CoRead can compute habit statistics locally.

The fourth task is implementing authentication, group creation, and deep-linked email invitations. The agent must implement Firebase Authentication supporting Google Sign-In and Email Link authentication. When a user creates a group and enters a partner's email address, CoRead writes the invitation to Firestore and triggers a lightweight email dispatch. The agent must configure Android App Links in `AndroidManifest.xml` with an intent filter capturing `[https://coread.app/invite?groupId=](https://coread.app/invite?groupId=){id}` (alongside your Render service domain as a fallback host). When the invited user taps the link, `MainActivity` extracts the `groupId` parameter, guides the user through authentication if they are not signed in, moves their email from `invitedEmails` to `memberIds` in a Firestore transaction, and navigates directly to the shared group dashboard.

The fifth task is building the custom Compose reading engine and the anti-cheating verification logic. The reading screen must use a `LazyColumn` backed by Room's `PagingSource` so only visible paragraphs reside in memory, ensuring smooth sixty-frames-per-second scrolling on low-end devices. To prevent cheating, the `ReaderViewModel` must observe `LazyListState.layoutInfo.visibleItemsInfo`. For every visible paragraph, the ViewModel calculates a minimum required dwell time based on a ceiling of 350 words per minute, which equals roughly 170 milliseconds per word. A background coroutine timer runs only while the activity is in the `RESUMED` lifecycle state and the user has interacted with the screen within the last ninety seconds. A paragraph is only marked as verified read in Room when it remains visible on screen for its required dwell duration. If the user scrolls past a paragraph faster than the threshold, the paragraph border turns amber and the progress tracker refuses to advance past that index until the user scrolls back and reads it at a realistic pace. Additionally, before a user can mark their daily milestone complete, the UI must verify that they have long-pressed at least one paragraph within the daily range to save a highlighted quote. Validated paragraph indices are batched and synced to the user's `members/{uid}` document in Firestore every thirty seconds or when leaving the screen.

The sixth task is building the dynamic milestone controller and the mutual streak pause system. On the CoRead group dashboard, any member can open a milestone adjustment sheet containing a segmented button for mode selection (Chapters, Word Count, or Custom Paragraph) and a continuous slider. As the user drags the word count slider, the ViewModel queries the local Room database using `SUM(wordCount)` starting from `startParagraphIndex` to dynamically preview the exact ending paragraph text in real time. Submitting a pace change or tapping the Pause Streak button writes a pending request object to the Firestore group document. The partner's app observes this state via a Firestore snapshot listener and displays a prominent banner at the top of the screen allowing them to approve or reject the pace change or streak freeze. When a pause request is approved, a Firestore transaction decrements `pauseTokensRemaining` by one and increments the deadline timestamp by twenty-four hours.

The seventh task is implementing the commentary, peer critique, and streak evaluation engine. At the bottom of the daily reading range, the reader unlocks the commentary composer. Submitting a commentary writes a document to `groups/{groupId}/commentaries/{dayNumber}_{uid}` containing the reflection text, the highlighted quote paragraph index, a `status` field set to `PENDING_REVIEW`, and a creation timestamp. In the UI, the partner's commentary card remains blurred using a graphical blur modifier until the local user's verified reading progress reaches `endParagraphIndex`, preventing spoilers. Once unlocked, the partner can read the commentary, write a critique reply, and tap either Approve or Request Revision. Tapping Approve updates the status to `APPROVED`. Tapping Request Revision sets the status to `REVISION_REQUESTED` and sends a push notification giving the author a twelve-hour grace window to edit their entry. The streak increments only when all active group members have reached `endParagraphIndex` and submitted commentaries that are either `APPROVED` or awaiting partner review within the twenty-four-hour review window. This separation guarantees a user is never penalized if they submit on time while their partner is asleep.

The eighth task is building the general chat, habit analytics, and notification workers. The general chat screen uses a paginated Firestore listener on the `messages` subcollection with an option to attach a specific paragraph reference chip to any message. For notifications and nudges, the agent must set up Firebase Cloud Messaging alongside a periodic `WorkManager` task called `DailyReminderWorker`. This worker queries `ReadingSessionLogEntity` in Room to calculate the median hour of day the user historically opens CoRead, scheduling a local notification fifteen minutes before that optimal window if the daily milestone is incomplete. Users can also tap a Nudge button on the dashboard, which writes a trigger document to Firestore and dispatches a high-priority push notification to the partner with context on how many words remain in today's goal.
